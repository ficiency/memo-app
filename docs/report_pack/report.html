Soal technical assessment · One memo, every firm

One memo engine: what it does, how we know, where it breaks

Luis Chapa9 Nov 2026FastAPI · Postgres (Supabase) · React · OpenAI

Each firm's memo format is stored as versioned data. A memo is built from that format and a deal's record, then edited in the browser, through an AI agent, or in PowerPoint and back. Every edit, from any of the three, goes through one server check before it lands, and nothing that cannot be applied is dropped: it is kept aside and shown. Three firms are loaded on one deal (Tidewell): Merrow (16:9 PowerPoint template), Corriemoor (4:3 template) and Lumen, the third firm, which sent only a written guide. Every number below comes from eval runs on the final code.

01How it works underneath

Three things are stored apart in Postgres: the deal record (every upload a new revision), the firm's spec (layouts, rules, brand; every approval a new version) and the memo, pinned to one of each until a person moves it. The memo is relational (memo → slide → box → paragraph → run), the same box model for the firm's layouts, the canvas and PowerPoint; history tables are only appended to. A figure is a run that remembers its record path. Five paths do all the work:

One editcanvas, agent or PowerPoint
  1. An operation arrives: what, which box, the box revision the editor saw
  2. The door: does this person hold the box? Do the firm's rules allow it (locked boxes, free area and grid, slide counts and order, figures never typed over)?
  3. Revision matches: rows written in one transaction, revision +1. Older: kept aside as a conflict
  4. Operation logged; everyone in the memo's room gets it over the websocket
Build and paintno model, $0
  1. Spec version + record revision + stage → the sections that stage requires, on their layouts
  2. Each box filled by its recipe: fixed words, a figure through the binding, a slot for the model or a person
  3. Text measured in the firm's real fonts with the template's insets; shrunk to the minimum or flagged
  4. PowerPoint written on the firm's own layouts, every slide and shape named with its id; PDF converted from it
PowerPoint backupload the edited file
  1. Read each shape's hidden id
  2. Compare with the export the file came from, not with the memo now
  3. Each difference becomes an operation
  4. The same door: applied, refused with a reason, or kept aside
Agentone request
  1. Code builds the context: the slide's boxes, what the spec puts in each, the rules, record figures by name and path
  2. One model call returns operations
  3. The door dry-runs them; errors go back to the model with the reason, at most twice
  4. A proposal: a person applies it change by change
Newer recorddata moves
  1. A new revision is announced live in every open memo
  2. See changes: each figure worked out again the way it was made (binding or record path), before → after
  3. Apply changes figures only; people's words stay

Kept aside: an edit that would overwrite newer work, stored as a visible conflict with its content. Pending: what the memo still needs from a person, computed from the memo as it is, never stored.

03Where the brief was silent: what we chose, and why

Identity: a hidden id, not titles or positions

People rename, reorder and move. The id in each shape's name survives PowerPoint saving the file (100% in the desktop suite).

Collisions: nobody's work is overwritten

One person holds a box at a time; a stale edit is kept aside; a newer record never applies itself. We chose visible conflicts over merging.

A typed-over figure is refused, not written back

The record changes only by a new revision. A typo in a deck should not change the facts every memo and firm reads.

Freedom only inside the firm's free areas

The canvas works on free slides, inside the free area, on the grid. Every picture is a pending, since it may be a chart pasted as an image.

04How we know it works

The evals act as people do: their own server, the API the screens use, websockets like the canvas, real PowerPoint files. Expected outcomes come from each firm's rules, never its name, so one suite runs on all three. Where layout matters, Microsoft PowerPoint is the judge, not our own measure. To prove the suites catch failures, two faults were planted in the canvas suite (pictures exported 0.1 in off; figures allowed to be typed over): it dropped from 100% to 60% and named both.

05The third firm: configuration or code

It took code once, and that was the most useful finding. Our first onboarding assumed a PowerPoint template from its first step and was run by engineers, with scripts and a separate model chat. Lumen sent only a written guide, so it showed that onboarding was shaped around "a firm with a template". We rebuilt it at the root: six steps inside the product, each model answer checked by code and approved by a person, layouts and a master designed from the guide when there is no template. That code is generic: no line of code names a firm (0 hits across backend, scripts and evals). With it, Lumen itself is all configuration: 10 layouts with a generated master, 81 boxes, 9 text roles, 16 formats, 55 rules, 57 recipe segments, 38 figures, 9 free areas. It also exposed one bug that hit every firm (tables with no column definitions were not measured), fixed for all. Not yet shown: a fourth firm going in with no code.

06Where it breaks, and how often

45 issues logged while building and testing, each with cause, area, severity and status. The evals found three late, all fixed at the root: tables without column definitions not measured, template bullets and indents lost, a picture PowerPoint saved without an embedded image refusing the whole file.

32 fixed2 partly fixed10 open1 not a bug

Weak today

  • highThe model binds a figure to a path of the right kind but sometimes the wrong datum (tenor shows 12 months, the deal is 36). Only the binding review by a person catches it.
  • medSome chart axes lack the firm's number format; onboarding can name chart series from their descriptions (fixed for Merrow only).
  • medPer-slide source lines and footnotes, and a risk matrix by probability × severity, still show "[no data]".
  • medA figure that is "some rows of a table" cannot be bound.
  • The 10 open issues come from earlier runs and were not re-confirmed on the final code.

Not tested

  • More than two people at once; disconnecting mid-edit (the memo reloads, missed messages are not replayed).
  • A person clicking in PowerPoint: the desktop suite drives PowerPoint through its automation interface.
  • Past memos' figures (their records were not given); Lumen rebuild (no past memos).
  • Load, and timings on anything but one laptop. Agent requests average 17–27 s per model call.

Not built

  • Continuing long text on another slide; promoting a slide into the template; template editing in the app; merging two people's typing in one box; Word output.
