Soal technical assessment · One memo, every firm

One memo engine: what it does, how we know, where it breaks

Luis Chapa9 Nov 2026FastAPI · Postgres (Supabase) · React · OpenAI

Each firm's memo format is stored as versioned data. A memo is built from it and a deal's record, then edited on the canvas, by an AI agent, or in PowerPoint and back; every edit goes through one server check, and what cannot be applied is kept aside and shown, never dropped. Three firms are loaded on one deal (Tidewell): Merrow (16:9 PowerPoint template), Corriemoor (4:3 template) and Lumen, the third firm, which sent only a written guide. Every number below comes from eval runs on the final code.

01How it works underneath

Three things are stored apart in Postgres, each versioned, so one changes without corrupting the others:

Deal record the facts

  • record_revisions: one per upload, with who and from which revision; a full copy, never overwritten.
  • record_values: one row per value: a path (table:pl_summary[FY26].revenue), kind, number, text or date, unit, period, forecast flag.
  • bindings: per firm and record format, where each figure comes from (path or formula).

Firm spec the rules; every row carries its version

  • sections, stages, order_constraints, rules: locked, mandatory, optional or free; slide counts; order; rules as type + parameters.
  • layouts, layout_zones: each layout's boxes (as elements) and free area.
  • text_roles, formats: size and minimum per role; number formats as fields (decimals, scale, symbol).
  • concepts, recipe_segments: named figures; what fills each box (fixed words, a figure, text to write).

Memo what people did

  • memos: pinned to a spec version and a record revision.
  • slides → elements (type, place in inches, role, lock, revision) → element_paragraphs → segments: text, a slot to write, or a figure that keeps its record path and value.
  • History, only appended to: operations, conflicts, memo_updates, pending_dismissals.

One box model serves the firm's layouts, the canvas and PowerPoint. Row-level security is on and the backend is the database's only client. Six paths do all the work:

Onboardingonce per firm; code checks each step, a person approves
  1. Materials: code reads every file
  2. House style: colours, fonts, formats
  3. Structure: sections, order, stages
  4. Layouts: from the template, or designed from the guide
  5. Recipe: what fills each box
  6. Rules: the guide's logic, typed
One editcanvas, agent or PowerPoint
  1. An operation arrives: what, which box, the box revision the editor saw
  2. The door: does this person hold the box? Do the firm's rules allow it (locked boxes, free area and grid, slide counts and order, figures never typed over)?
  3. Revision matches: rows written in one transaction, revision +1. Older: kept aside as a conflict
  4. Operation logged; everyone in the memo's room gets it over the websocket
Build and paintno model, $0
  1. Spec version + record revision + stage → the sections that stage requires, on their layouts
  2. Each box filled by its recipe: fixed words, a figure through the binding, a slot for the model or a person
  3. Text measured in the firm's real fonts with the template's insets; shrunk to the minimum or flagged
  4. PowerPoint written on the firm's own layouts, every slide and shape named with its id; PDF converted from it
PowerPoint backupload the edited file
  1. Read each shape's hidden id
  2. Compare with the export the file came from, not with the memo now
  3. Each difference becomes an operation
  4. The same door: applied, refused with a reason, or kept aside
Agentone request
  1. Code builds the context: the slide's boxes, what the spec puts in each, the rules, record figures by name and path
  2. One model call returns operations
  3. The door dry-runs them; errors go back to the model with the reason, at most twice
  4. A proposal: a person applies it change by change
Newer recorddata moves
  1. A new revision is announced live in every open memo
  2. See changes: each figure worked out again the way it was made (binding or record path), before → after
  3. Apply changes figures only; people's words stay

Kept aside: an edit that would overwrite newer work, kept as a visible conflict (a box you edit in PowerPoint that a colleague rewrote since your export). Pending: what the memo still needs from a person, worked out by code (a figure the record lacks, a box to write, a picture to confirm).

03Where the brief was silent: what we chose, and why

  • Identity is a hidden id in each shape's name, not titles or positions: people rename, reorder and move. It survives PowerPoint saving the file.
  • Collisions never overwrite: one person holds a box at a time, a stale edit is kept aside, a newer record never applies itself.
  • A typed-over figure is refused, not written back: a typo in a deck should not change the facts every memo and firm reads.
  • Freedom only inside the firm's free areas, on the grid; every picture is a pending, since it may be a chart pasted as an image.

04The screens where people check and steer

  • Firm setup: each onboarding step's answer, what code could not resolve, every guide-versus-template conflict with both sides' evidence; nothing lands unapproved.
  • Deal record: upload a file or edit values in place; each save is a new revision; a changed number offers to update its twins.
  • Bindings: where each figure comes from, flagged (no value, broken path, value moved, a twin, wrong kind); a person can change any binding.
  • In the memo: pendings worked out by code (no model), agent proposals applied change by change, See changes before a newer record or template lands.

06The third firm: configuration or code

It took code once, and that was the most useful finding. Our first onboarding assumed a PowerPoint template and was run by engineers by hand; Lumen, with only a guide, showed it was shaped around "a firm with a template". We rebuilt it at the root: six steps inside the product, each model answer checked by code and approved by a person, layouts and a master designed from the guide when there is no template. That code is generic: no line of code names a firm (0 hits in backend, scripts, evals). With it, Lumen itself is all configuration: 10 layouts with a generated master, 81 boxes, 16 formats, 55 rules, 57 recipe segments, 38 figures. It also exposed a bug in every firm (unmeasured tables), fixed for all.

07Where it breaks, and how often

45 issues logged while building and testing, each with cause, severity and status. The evals found three late, fixed at the root: unmeasured tables, lost template bullets and indents, a picture PowerPoint saved without an embedded image refusing the whole file. The 10 open ones are from earlier runs, not re-confirmed on the final code.

32 fixed2 partly fixed10 open1 not a bug

Weak today

  • highA binding can pick a value of the right kind but the wrong datum (tenor 12 months; the deal is 36). Only a person's review catches it.
  • medSome chart axes lack the firm's number format; chart series can be named from descriptions (fixed for Merrow).
  • medPer-slide source lines and footnotes, and a risk matrix by probability × severity, still show "[no data]".
  • medA figure that is "some rows of a table" cannot be bound.

Not tested

  • More than two people at once; reconnecting mid-edit (the memo reloads; nothing replayed).
  • A person clicking in PowerPoint (the suite drives it by automation).
  • Past memos' figures (records not given); onboarding from a template only or past memos only.
  • Load; every timing is from one laptop against the hosted database.

08What we would do next, in order

  1. Bindings checked, not only reviewed: against the unit, period and range the guide and past memos give each figure, so a wrong datum (the tenor) is flagged.
  2. Long content that continues not built onto a continuation slide by the firm's rules. Cut: each firm needs its own split rules, and exact measuring came first; today it is reported, never shipped cut.
  3. Promote a slide into the template not built As a new spec version. Cut: it sits on template editing (next item), and the PowerPoint round trip mattered more.
  4. Template editing in the app not built As checked operations on the spec. Cut at the start: firms arrive with a template or guide, so learning from it came first.
  5. Reconnect and replay not built missed operations, then a load test. Cut: on reconnect the memo reloads from the server; no saved work is lost.
